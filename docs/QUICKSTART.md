# Bridge Quickstart

One contract. Every language. Zero interoperability drift.

This guide takes you from an empty directory to generated, verified Go,
Rust, TypeScript and Python types — and shows how to evolve a contract
without breaking consumers.

> **Prerequisites:** Node 22+ and npm. The Bridge CLI ships in this
> repository (`packages/bridge-cli`); build the workspace once:
>
> ```sh
> npm install
> npm run build
> ```
>
> The `bridge` binary then lives at `packages/bridge-cli/dist/bin/bridge.js`
> (link it or add an alias as you prefer).

---

## 1. Scaffold a project

```sh
bridge init payments-service
```

Creates a ready-to-edit project layout with a first `.bridge` contract and
a `bridge.json`. Prefer manual? Any directory with `*.bridge` files
works — Bridge has no required project file:

```
payments-service/
  bridge.bridge        # or any <name>.bridge files
```

## 2. Write your first contract

```bridge
package payments.v1

/// Money amount in the smallest currency unit.
type Money {
    amount: int64
    currency: string @length(3)
}

type CreatePaymentRequest {
    customer_id: uuid
    amount: Money
}

type Payment {
    id: uuid
    customer_id: uuid
    amount: Money
    status: PaymentStatus
    created_at: timestamp
}

enum PaymentStatus {
    PENDING
    COMPLETED
    FAILED
}

service Payments {
    CreatePayment(CreatePaymentRequest) -> Payment
}
```

Save it as `payments.bridge`. The full language — enums, unions, aliases,
events, sets, maps, defaults, deprecations — is documented in
[IDL_REFERENCE](./IDL_REFERENCE.md).

## 3. Validate and format

```sh
bridge validate payments.bridge
```

Compiles the contract through the full pipeline (lexer → parser → semantic
analysis → canonical IR) and prints human-readable diagnostics with source
snippets and did-you-mean hints:

```
payments.bridge:8:13: error BR2001: Unknown type `mony`.

  8 |     amount: mony
    |             ^

  Did you mean `Money`?
```

```sh
bridge fmt payments.bridge        # canonical formatting (idempotent), in place
bridge lint payments.bridge       # style warnings: naming conventions, etc.
```

Formatting never changes meaning — only layout (4-space indent, one field
per line, `///` doc comments preserved). See
[IDL_REFERENCE](./IDL_REFERENCE.md#diagnostics) for the diagnostic format.

## 4. Generate code

```sh
bridge generate payments.bridge --language go         # → ./generated/go
bridge generate payments.bridge --language typescript --out ./clients/web
bridge generate payments.bridge --language python
bridge generate payments.bridge --language rust
```

Every generated project is dependency-free (Go stdlib / serde / plain TS /
stdlib Python dataclasses) and byte-deterministic: regenerating never
produces diffs churn. Generated headers read
`Code generated by bridge DO NOT EDIT.`

Runnable examples for every language pair live in
[`examples/`](../examples) — start with
[go-python](../examples/go-python), which executes a live Python round-trip
of the generated code.

## 5. Evolve without breaking anyone

Draft the next revision and compare it against the published one:

```sh
bridge diff v1.payments.bridge v2.payments.bridge
```

```
BRIDGE COMPATIBILITY REPORT
package: payments.v1

❌ Breaking: Field renamed: Payment.currency → Payment.reference
⚠ Added enum value: PaymentStatus.REFUNDED

Summary: 0 safe, 1 warnings, 1 breaking, 0 unknown
Verdict: BREAKING
Compatibility: FAILED
```

Then gate it in CI (exit `1` blocks the pipeline):

```sh
bridge check v1.payments.bridge v2.payments.bridge
```

`check` implements the strict gate: BREAKING and UNKNOWN verdicts fail,
SAFE and WARNING pass (use `bridge check --compatible` during an
explicit migration window). The full classification matrix and a
GitHub Actions recipe: [COMPATIBILITY](./COMPATIBILITY.md).

## 6. Publish to the registry

```sh
bridge publish payments.bridge --registry .bridge-registry
bridge versions payments.v1 --registry .bridge-registry
bridge search payments --registry .bridge-registry
bridge inspect payments.v1 v1 --registry .bridge-registry
bridge pull payments.v1 v1 --registry .bridge-registry
```

The registry is local and content-addressed: a version's identity is the
SHA-256 of its canonical IR, republishing identical content is a no-op,
and published versions are immutable. Consumers can be found before you
change anything: `dependents` (exposed via the registry API — see the
[registry example](../examples/registry)) lists contracts that import
yours.

Publishing to a running [registry service](../packages/bridge-registry-service)
adds authentication and tenancy (`--registry <url> --org org --project
project --token token`), and — when the service is configured with
required ed25519 artifact signing — a signature: pass
`--signing-key-id <id> --signing-key-file <private-key.pem>` (or
`BRIDGE_SIGNING_KEY_ID` / `BRIDGE_SIGNING_KEY`) with a key whose public
half is configured on the service. The signature covers the canonical
JSON of the publish payload, so any content change invalidates it.

## 7. Troubleshoot your setup

```sh
bridge doctor     # toolchain + workspace health check
bridge version    # compiler / generator versions
```

## The API-first alternative

Everything the CLI does is a thin wrapper over the workspace packages, so
scripts and services can skip the shell:

```js
import { compileSource, shortHash } from '@bridge/core';
import { generate } from '@bridge/generators';
import { readFileSync } from 'node:fs';

const source = readFileSync('payments.bridge', 'utf8');
const result = compileSource(source, 'payments.bridge');
if (!result.ok) {
  for (const d of result.diagnostics) console.error(d);
  process.exit(1);
}
console.log(shortHash(result.ir)); // e.g. 1f7292582f39

const files = generate(result.ir, { language: 'go' });
// files: [{ path: 'go.mod', content: '...' }, { path: 'types.go', ... }]
```

The same one-liners drive every
[example demo](../examples) in this repository.
